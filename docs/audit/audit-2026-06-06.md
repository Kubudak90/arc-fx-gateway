# Arcora Full-Scope Security Audit

Date: 2026-06-06
Commit: `03db7f171cfa67056026a59b7995b3ae8e7f6874`
Scope: first-party runtime code in `packages/app`, `packages/shop`,
`packages/sdk`, `packages/sdk-react`, `packages/contracts`, and `ops`

## Executive Summary

The audit found two High, three Medium, and six Low severity issues. The two
highest-priority problems cross trust boundaries:

1. The relayer accepts a gateway address from a PostgreSQL result over a
   connection that can disable certificate verification, then approves that
   address to spend settlement tokens.
2. Browser and React SDK guidance exposes the same `ak_live_` bearer credential
   used for privileged invoice creation and merchant-data access.

The current Arc testnet and pre-revenue deployment reduces immediate monetary
impact for several findings. These controls do not make the affected designs
appropriate for mainnet or automated fulfillment.

| Severity | Count (as filed) | Count (verified) |
|---|---:|---:|
| High | 2 | 1 |
| Medium | 3 | 4 |
| Low | 6 | 6 |
| Suppressed | 1 | 1 |

The "verified" column reflects the independent re-scoring recorded in the next
section. AFG-010 was re-scored High → Medium; all other severities held.

- **AFG-010 re-scored High → Medium.** The mechanism is real (the relayer uses
  the DB `gateway_address` as both the ERC-20 spender and the `settleInvoice`
  target with no env allowlist), but exploitation requires (a) an active

  the dotted form it already handles; the high-impact path is AFG-001's unpinned
  second resolution, which skips this classifier entirely.

## Findings

### AFG-010 - Relayer DB MITM can redirect settlement approval

**Severity: High → Medium (re-scored on verification) | Confidence: High**

The relayer creates its PostgreSQL pool with
`ssl: { rejectUnauthorized: false }`. It then trusts
`invoices.gateway_address` from the claimed database row as both the ERC-20
spender and the `settleInvoice` call target. A network-positioned database MITM
can replace that returned address. After the swap, the relayer approves the
attacker-selected address for the exact gross payout, enabling theft of each
intercepted settlement.

The attack is conditional on the deployed DSN leaving the explicit insecure TLS
setting effective. A DSN that enables full verification can defeat the MITM,
but the repository does not enforce or verify that deployment state.

> **Verified (2026-06-06): TRUE, re-scored High → Medium.** `gatewayFor()`
> (`ops/relayer/run.ts:149-152`) does resolve the spender/settle target from the
> mutable DB column with no env cross-check (the `?? GATEWAY` fallback only
> covers the NULL case). But (a) `approve()` alone moves no funds — theft also
> requires the attacker to deploy a contract at the swapped address whose
> `settleInvoice` calls `transferFrom` on the granted allowance; (b) the column
> is env-pinned at write time (the indexer only persists addresses it watched
> via `GATEWAY_ADDRESS`), so this is a missing read-time re-validation rather
> than an open injection channel; and (c) exploitation depends on the AFG-011
> DB-MITM precondition. Real defense-in-depth gap, Medium.

Evidence:

- `ops/relayer/run.ts:108`
- `ops/relayer/run.ts:149-152`
- `ops/relayer/run.ts:407-433`

Remediation:

- Require CA and hostname verification for PostgreSQL.
- Reject startup when the effective TLS configuration is not verify-full.
- Bind each row to an allowlisted deployment address or expected code hash.
- Never derive an ERC-20 spender solely from a mutable database result.

Detailed validation:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-010/validation.md`

### AFG-019 - Browser SDK exposes a privileged merchant API key

**Severity: High | Confidence: High**

The browser, CDN, and React SDK documentation instructs merchants to place an
`ak_live_` key in public client code. The server has no distinct publishable
credential: this is the same bearer key used to create invoices, consume
server-wallet gas, list merchant escrows, and read authenticated invoice data.

Anyone visiting an integrated storefront can recover the key from the bundle,
page, props, environment-inlined values, or network request and replay it
outside the browser. CORS and redirect-origin controls do not provide an
authorization boundary.

> **Verified (2026-06-06): TRUE.** Every sub-claim confirmed: the CDN/React/docs
> samples place `ak_live_` in browser code (the docs use `NEXT_PUBLIC_ARCORA_KEY`,
> which Next.js inlines into the client bundle), with no server-side-only warning;
> `client.ts` sends the same key as `X-Arcora-Api-Key` for create-invoice and
> escrow-listing; the only key prefix in `lib/auth/apikey.ts` is `ak_live_`
> (no `pk_`/publishable type exists); `/api/invoices` CORS is `*` and
> `assertOriginAllowed` only validates the merchant's redirect URL, not the
> caller. High stands.

Evidence:

- `packages/sdk/README.md`
- `packages/sdk-react/README.md:15-69`
- `packages/app/app/docs/sdk/page.tsx:81-117`
- `packages/sdk/src/client.ts:32-104`
- `packages/app/app/api/invoices/route.ts:69-105`
- `packages/app/app/api/merchant/escrows/route.ts:21-79`

Remediation:

- Keep `ak_live_` credentials server-side only.
- Introduce a separate publishable key type with narrow capabilities and origin
  binding.
- Prefer short-lived checkout-session tokens minted by the merchant backend.
- Do not let browser credentials list escrows or read private invoice fields.
- Create checkout amounts from server-approved products or signed cart data.

Detailed validation:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-019/validation.md`

### AFG-001 - Webhook DNS validation is vulnerable to rebinding

**Severity: Medium | Confidence: High**

The webhook daemon resolves and checks a merchant hostname, then calls global
`fetch()` with the original URL. The connection performs a separate DNS lookup,
so the checked public address is not pinned to the socket. A bounded local PoC
returned a public address during validation and loopback during fetch; the
internal listener received the POST.

Production HTTPS and normal certificate verification substantially reduce the
reachable target set. The checked-in service does not set `NODE_ENV=production`,
so the HTTPS-only branch is not guaranteed by repository configuration.

> **Verified (2026-06-06): TRUE.** Validation resolves at `run.ts:172` and
> `fetch(row.url)` re-resolves independently at `run.ts:203` with no
> lookup-pinning (no custom `lookup`/dispatcher anywhere) — a genuine
> check-then-use window. The HTTPS-only guard is gated on
> `NODE_ENV === "production"` (`run.ts:169`), and the checked-in
> `arcora-webhooks.service` does not set it. Mitigation the audit correctly
> credits: redirects are `manual` and any 3xx is failed, so redirect-to-internal
> is closed. Medium stands.

Evidence:

- `ops/webhooks/run.ts:153-180`
- `ops/webhooks/run.ts:182-214`
- `ops/webhooks/arcora-webhooks.service`

Remediation:

- Resolve once and pin a validated address through the HTTP client's lookup
  hook while preserving the original hostname for Host/SNI verification.
- Apply the policy on every new connection and keep redirects disabled.
- Set and assert production mode at daemon startup.

Detailed validation and PoC:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-001/validation.md`

### AFG-003 - Shop trusts client-supplied product prices and quantities

**Severity: Medium | Confidence: High**

The public shop endpoint accepts complete cart objects and computes the Arcora
invoice amount directly from client-supplied `price` and `qty`. It does not look
up the SKU in the server-owned catalog or enforce server-side quantity bounds.
A local HTTP reproduction created an authenticated upstream request for ten
tees at `$0.01` instead of the catalog total of `$99.90`.

The current testnet deployment and manual fulfillment reduce direct loss.
Moving this flow to real-value settlement or automated fulfillment without a
fix would materially increase severity.

> **Verified (2026-06-06): TRUE.** `start/route.ts` parses the body with a bare
> cast (no zod) and computes `subtotal = Σ price·qty` from client values
> (`route.ts:52-59`), never consulting the existing server catalog
> (`packages/shop/lib/products.ts`). The "cap qty to 10" is client-only
> (`AddToCartForm.tsx`), trivially bypassed by a direct POST. Repro confirmed.
> Medium stands.

Evidence:

- `packages/shop/app/checkout/page.tsx:45-49`
- `packages/shop/app/api/checkout/start/route.ts:34-59`
- `packages/shop/app/api/checkout/start/route.ts:80-119`

Remediation:

- Accept only SKU, option identifiers, and bounded integer quantities.
- Resolve price and product data from the server catalog.
- Persist a server-side order and fulfill against that record, not
  client-authored invoice metadata.

Detailed validation:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-003/validation.md`

### AFG-011 - Ops daemons disable PostgreSQL certificate verification

**Severity: Medium | Confidence: High**

The relayer, indexer, and webhook dispatcher use
`ssl: { rejectUnauthorized: false }`. Outside the direct fund-loss chain in
AFG-010, a database MITM can still manipulate indexed status and queued webhook
destinations or payloads, disrupt processing, and observe or alter daemon
traffic.

Evidence:

- `ops/relayer/run.ts:108`
- `ops/indexer/run.ts:64`
- `ops/webhooks/run.ts:52`
- `ops/relayer/replay.ts:46`, `ops/relayer/e2e-test.ts:73`,
  `ops/relayer/e2e-twowallet.ts:71`, `ops/indexer/replay.ts:94`

> **Verified (2026-06-06): TRUE, under-counted.** The pattern is present at 7
> first-party sites (three daemons + the four scripts above), not 3. It is the
> documented Supabase self-signed-pooler workaround (`db_supabase_2026-05-20`);
> the correct fix is pinning Supabase's CA (`ca:` / `sslrootcert`) and setting
> `rejectUnauthorized: true`, not disabling verification wholesale.

Remediation:

- Centralize a strict PostgreSQL client configuration.
- Pin the provider CA and require hostname verification.
- Add a startup self-test that records only sanitized TLS mode and rejects
  insecure production configuration.

### AFG-004 - Anonymous shop requests spend merchant and server resources

**Severity: Low | Confidence: High**

`POST /api/checkout/start` is anonymous and uses the shop's server-held API key
to create a real on-chain invoice. Attackers can create unpaid invoice noise and
consume the shop's own merchant rate-limit bucket, RPC quota, and server-wallet
gas. This is also reachable through AFG-003.

> **Verified (2026-06-06): TRUE, over-stated.** The anonymous endpoint and the
> real `createInvoiceFor` on-chain write are confirmed. Correction: the upstream
> limiter (`packages/app/app/api/invoices/route.ts`) is keyed on `merchant.id`
> and runs after auth, capping the shop's key at 60 invoices / 60 s — an
> attacker cannot exhaust *other* merchants' buckets, and flooding is bounded.
> (Note the limiter fails open on a Postgres outage, a narrow residual.) Low.

Remediation: add abuse controls before the privileged call, including
rate-limiting by trusted client identity, challenge/bot controls, idempotency,
and a server-side pending-order record.

### AFG-002 - Webhook private-IP classifier misses IPv6 transition forms

**Severity: Low | Confidence: Medium**

The local IPv6 classifier handles common loopback, link-local, unique-local,
multicast, and dotted IPv4-mapped forms, but textual transition forms such as
hex-encoded IPv4-mapped addresses are not normalized before classification.

> **Verified (2026-06-06): TRUE, narrow reach.** Confirmed bypasses against the
> classifier: `::ffff:7f00:1` (127.0.0.1), `::ffff:a00:1` (10.0.0.1),
> `0:0:0:0:0:ffff:127.0.0.1`, `64:ff9b::7f00:1` (NAT64), `2002:7f00:1::` (6to4)
> all read as public. But the classifier runs only on `dns.lookup` output, which
> canonically returns the dotted form it already handles, so standalone reach is
> limited; the impactful path is AFG-001's unpinned second resolution, which
> skips this classifier entirely. Fix both with one shared normalize-then-deny.

Remediation: parse addresses with a maintained IP library, normalize IPv4-mapped
IPv6, and deny all special-purpose ranges using a single shared implementation.

### AFG-005 - Compliance and payout-read failures default to fail-open

**Severity: Low | Confidence: High**

Invoice creation defaults `COMPLIANCE_FAIL_OPEN_FOR_INVOICE` to true, and the
provider defaults to `noop`. RPC payout-address read errors fall back to
screening the identity address; provider errors permit invoice creation.
This is documented for testnet but is a dangerous supported production
configuration.

Evidence:

- `packages/app/app/api/invoices/route.ts:165-218`
- `packages/app/lib/compliance/factory.ts:7-20`

> **Verified (2026-06-06): TRUE.** `factory.ts:16` defaults the provider to
> `noop`; `COMPLIANCE_FAIL_OPEN_FOR_INVOICE` defaults true via
> `(... ?? "true") !== "false"` at both `route.ts:188` (RPC payout-read error)
> and `route.ts:214` (provider error). On RPC error the code keeps screening
> `merchant.address` (the identity wallet) rather than the real payout address;
> on provider error `payoutScreen` stays null and the reject/review gates are
> skipped. Low (default-config risk) stands.

Remediation: fail startup in production/mainnet unless a real provider is
configured and fail closed for payout reads and screening failures.

### AFG-006 - Merchant state changes have inconsistent CSRF enforcement

**Severity: Low | Confidence: High**

Webhook mutation and secret rotation use `isSameOrigin`, while API-key
rotation, allowed-origin mutation, and merchant bootstrap do not. The host-only
`SameSite=Lax` session cookie blocks common cross-site POST/fetch attacks, so
this is defense-in-depth rather than a broadly exploitable CSRF.

Evidence:

- `packages/app/app/api/merchant/api-key/route.ts:8-21`
- `packages/app/app/api/merchant/origins/route.ts:19-65`
- `packages/app/app/api/merchant/bootstrap/route.ts:23-95`
- `packages/app/app/api/merchant/webhook/route.ts:14-55`

> **Verified (2026-06-06): TRUE.** Only `merchant/webhook` (PATCH + POST) calls
> `isSameOrigin`; `api-key` (POST), `origins` (PATCH), and `bootstrap` (POST) do
> not import or call it. The downgrade premise also holds: the `arcfx_session`
> cookie is `SameSite=Lax` + host-only (`lib/auth/session.ts:44-52`), and all
> three unguarded routes are POST/PATCH (not top-level GET), so Lax blocks the
> realistic cross-site attack. Low (defense-in-depth) stands.

Remediation: apply the same origin/referer guard to every session-authenticated
state-changing route and add route-level regression tests.

### AFG-009 - Unbounded decimal strings are parsed before numeric limits

**Severity: Low | Confidence: High**

Quote and submit routes accept arbitrary-length digit strings and convert them
to `BigInt` before enforcing practical maxima. A bounded benchmark showed about
50 ms for one million digits and about 566 ms for five million digits. No
request-body size cap is enforced upstream (these are App Router route handlers,
not Server Actions, so Next's 1 MB body cap does not apply), and the schemas
themselves impose no string-length or precision bound before conversion.

Evidence:

- `packages/app/app/api/checkout/quote/route.ts:20-23,55`
- `packages/app/app/api/quote/route.ts:33`
- `packages/app/app/api/checkout/submit/route.ts:60,101-108`

> **Verified (2026-06-06): TRUE, wording corrected.** All three routes *do*
> apply a per-IP `takeToken` rate limit (quote 30/60 s, submit 10/60 s), so the
> original "rate controls ... not enforced" was misleading — the missing
> control is the body-size cap and the in-schema length/precision bound. Note
> `/api/quote` already rejects oversized *values* (`MAX_QUOTE_IN = 10**18`) but
> still incurs the parse cost; the unbounded-parse exposure is real on all
> three. Low (arguably generous) stands.

Remediation: cap string length and decimal precision in the schema before any
`BigInt` conversion.

### AFG-013 - Refund remains callable after the advertised refund window

**Severity: Low | Confidence: High**

`refundInvoice()` does not check `claimableAt`. At and after that timestamp,
refund and permissionless claim are both valid; transaction ordering decides
whether the payer is refunded or the merchant receives the escrow. The issue
requires a merchant, admin, or active refund delegate and funds can only return
to the recorded payer.

The migration documentation acknowledges first-transaction-wins behavior, but
the contract NatSpec, product docs, API state model, and UI describe a hard
refund cutoff. The repository therefore exposes conflicting invariants.

Evidence:

- `packages/contracts/src/ArcFXGateway.sol:316-335`
- `packages/contracts/src/ArcFXGateway.sol:358-379`

> **Verified (2026-06-06): TRUE.** `refundInvoice()` has no `claimableAt` check
> (its only `block.timestamp` use is the delegate `expiresAt` check); `claim()`
> requires `block.timestamp >= claimableAt`. Both gate on `status == Paid`, so
> at/after `claimableAt` they race by tx ordering. The UI hard-gates the refund
> button on `now < claimableAt` (`RefundButton.tsx:34-43`) and the quickstart
> docs imply a hard cutoff, so the code/spec divergence is real. Nuance: the
> `migration` doc *does* describe the race accurately, so the contradiction is
> not uniform across all docs. Low stands.

Remediation: either enforce `block.timestamp < claimableAt` in
`refundInvoice()`, or update all public product and API semantics to describe
the soft window explicitly.

Detailed validation:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-013/validation.md`

### AFG-021 - Core daemons run as root without systemd sandboxing

**Severity: Low | Confidence: High**

The relayer, indexer, and webhook systemd units operate from `/root` and their
dedicated `User=` and `Group=` directives are commented out. The units also
lack common sandboxing directives. This amplifies the impact of SSRF, runtime,
dependency, or daemon compromise.

> **Verified (2026-06-06): TRUE.** All three units set `WorkingDirectory` under
> `/root/arcora-ops/*`, have `# User=arcora-ops` / `# Group=arcora-ops`
> commented out (so they run as root), and carry zero hardening directives
> (`NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, `PrivateTmp`,
> `ReadWritePaths` all absent). Self-documented as a known mainnet pre-flight
> item. Low stands.

Remediation: move runtime files outside `/root`, enable a dedicated user/group,
restrict filesystem access and capabilities, and apply systemd hardening such
as `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, and a narrow
`ReadWritePaths` set.

## Suppressed Candidate

### AFG-014 - Hosted checkout metadata disclosure

The public page reads invoice metadata and contains a line-item rendering sink,
but all supported creation paths restrict metadata values to strings. The
nested `metadata.lineItems` shape required by the sink cannot currently be
created, and the shop's flat shipping/order fields are ignored by that
component. The candidate is suppressed with high confidence.

Residual risk: invoice IDs are enumerable from chain events, so any future
schema relaxation that makes `lineItems` writable would make those fields
public.

> **Verified (2026-06-06): suppression JUSTIFIED.** The `metadata.lineItems`
> sink in `InvoiceCard.tsx` is reachable from the public page, but the only
> insert path (`/api/invoices`, schema `z.record(z.string().max(256))`) rejects
> nested arrays/objects, the only update (`checkout/submit`) never touches
> metadata, and the shop flattens its cart into a single `items_json` string the
> sink ignores. The schema-less `jsonb` column + enumerable IDs make this a
> regression-watch item, not a present finding.

Detailed validation:
`docs/audit/2026-06-06-full-scope/artifacts/validation/AFG-014/validation.md`

## Remediation Order

Post-verification ordering. AFG-010 and AFG-011 are coupled — pinning the
provider CA (AFG-011) removes the DB-MITM precondition that makes AFG-010
reachable — so they are sequenced together; the per-finding plan is in
`docs/audit/2026-06-06-full-scope/remediation-plan.md`.

1. Remove `ak_live_` keys from browser integration guidance and design a scoped
   publishable/session-token model (AFG-019, only confirmed High).
2. Pin strict DB TLS (provider CA) across all ops daemons + scripts, then add
   the relayer read-time gateway re-validation (AFG-011 → AFG-010 together).
3. Recompute shop prices from a server-owned catalog and add abuse controls
   (AFG-003 + AFG-004).
4. Pin webhook DNS resolution to the actual connection and assert production
   mode (AFG-001 + AFG-002, one shared normalize-then-deny).
5. Run ops daemons unprivileged with systemd sandboxing (AFG-021).
6. Resolve compliance fail-open and refund-window semantics before mainnet
   (AFG-005 + AFG-013).
7. Close the remaining input-validation and CSRF consistency gaps
   (AFG-009 + AFG-006).

## Scope Notes

The review covered first-party reachable/runtime surfaces. Vendored Solidity
libraries, generated build output, dependency source, historical documents,
test fixtures, and deployment artifacts were excluded from line-by-line manual
review except where needed to validate an attack path. No product source code
was changed during the audit.
